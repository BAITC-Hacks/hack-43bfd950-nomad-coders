# Передача frontend капитану

Ветка: codex/web-ui. База: origin/main 6d496b3. Работа выполнена только в frontend/, сгенерированные типы не изменены. Автор Git настроен пользователем. Передача подготовлена коммитом в codex/web-ui; публикация выполняется только в origin/codex/web-ui. SHA передаётся в сообщении капитану.

## Что работает

Интерфейс разделён на DataPage, RecommendationsPage, OrderPage, ExplanationPanel, общий вывод ошибок и ленивый HistoryChart. Светлая тема соответствует ТЗ, основные действия находятся вверху, таблицы прокручиваются внутри страницы. Явно отмечается синтетика.

Данные: выбор набора и поставщика, версия, происхождение, дата загрузки, проблемы данных; несколько XLSX с именами и размерами, удаление, проверка расширения и лимита 30 МиБ. Реальный набор допускает настройки даты, срока 0–365, пересмотра 1–365, буфера 0–365 и источника спроса. Демо остаётся фиксированным. Изменения делают старые рекомендации неактуальными.

Рекомендации: поиск по названию/SKU/артикулу, фильтры поставщика, кода категории, срочности и проблем; сортировка количества/статуса, страницы 50/100, счётчики товаров без суммирования разных единиц. Ноль и null различаются. Неизвестная единица и blocking issue блокируют выбор. Выбор сохраняется при фильтрации, отмечены скрытые строки. Один заказ содержит товары одного поставщика.

Объяснение: исходный текст, компоненты, raw_need, отдельные minimum/multiple, даты и источники, допущения, проблемы, поставки, аномалии. История показывает только переданные ряды; пропуски не превращаются в нули. Есть русская легенда, разные штрихи, таблица данных графика. Панель закрывается Escape и возвращает фокус; поздний ответ закрытого товара игнорируется.

Заказ: исходная рекомендация, правка и обязательная причина, неотрицательное конечное число, сохранение через expected_revision, защита несохранённых правок. При 409 введённые значения остаются до явной отмены или загрузки сервера. Восстанавливаются последний заказ и связанный расчёт. Согласование использует серверную revision. CSV скачивается из ответа API; сетевые ошибки и 409 показываются внутри интерфейса.

## Проверки

Команда из корня:

    powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1 -Browser

Результат 23.09.2026: 22 backend-теста прошли; TypeScript и Vite build прошли; 13 Playwright-тестов прошли за 18,3 с. Проверен собранный интерфейс через FastAPI на 8009 с временной SQLite, реальным API, сохранением нулевой правки после refresh, согласованием, содержимым CSV и снятием согласования после изменения. Дополнительные явно тестовые ответы проверяют 409, 501, сетевые ошибки и 1001 товар.

Проверены 1366×768, 1440×900, 768×1024, 390×844. Нет горизонтального переполнения документа; таблица имеет собственную прокрутку. Проверены Escape и удержание/возврат фокуса. Снимки визуально просмотрены. Основной JS: 262,09 КБ (81,13 КБ gzip); график загружается отдельно: 366,94 КБ. Новые зависимости не добавлены.

В окружении был не установлен Chromium. Загружен для текущего Playwright через встроенный Node с доверенными сертификатами Windows. Проверка TLS не отключалась. У backend осталось существующее предупреждение о deprecated использовании httpx в Starlette TestClient; чужие зависимости не менялись.

## Что ожидается от backend

Импорт реальных книг и реальный прогноз пока возвращают 501; интерфейс показывает ошибку, не подменяет ответ синтетикой. Положительный ответ импорта должен содержать Dataset и появиться в GET /api/datasets. Настройки передаются существующей схемой.

Для отдельного блока сезонности нужно добавить коэффициенты в общий контракт капитаном. Сейчас выводятся только существующие компоненты и объяснение; коэффициенты не вычисляются в браузере. Для XLSX и списка всех заказов пока нет API, фиктивные кнопки не добавлены. Публичный деплой и проверка на реальных данных остаются у капитана.

Перед интеграцией проверить изменения ветки и повторить check.ps1 -Browser. main и чужие ветки не изменялись; отправка решения на платформу не выполнялась.
