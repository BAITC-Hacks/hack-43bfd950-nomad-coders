# Общий контракт

Владелец — капитан/backend. Источник истины: Pydantic в backend/app/contracts/models.py. Команда scripts/contracts.ps1 экспортирует OpenAPI, синтетические примеры и TypeScript-типы. Не редактировать сгенерированные файлы вручную.

fixtures/ содержит только явно синтетические данные. Количество 144 проверяет интеграцию, а не наличие реального алгоритма прогноза. null означает неизвестное количество; 0 — достоверное отсутствие потребности в заказе. При неподключённом импорте или движке API отвечает 501.

Импорт: import_workbooks(list[SourceWorkbook], supplier) -> NormalizedDataset. SourceWorkbook содержит filename и content (bytes), без сохранения оригинала в Git. Расчёт: calculate(NormalizedDataset, CalculationSettings) -> EngineOutput. Расчёт не читает файлы и не обращается к SQLite. Service назначает идентификатор расчёта и подставляет его в объяснения; recommendation.id одинаков во всех связанных объектах.

SKU и артикулы всегда строки. Даты ISO 8601, дата отчёта отделена от даты загрузки. Поставщик systeme/iek/demo. Неизвестная единица остаётся null. Для сопоставления используйте пару supplier + sku. Категории не получают придуманных названий.

Настройки дня для будущего движка: as_of — конец дня снимка; первый прогнозный день — следующий календарный день. Срок L=0 означает первый прогнозный день. Поступления учитываются в начале своей даты; поставки до даты снимка не добавляются к уже снятому остатку автоматически. Stockout.start/end включают обе даты. Реализация математических правил остаётся следующим этапом backend.

GET /api/datasets -> массив Dataset. POST принимает multipart files (повторяющееся поле) и supplier. POST /api/calculations принимает dataset_id, settings и необязательный supplier. Результат неизменяем; пояснение получается по item id из результата.

POST /api/orders создаёт заказ одного поставщика из одного расчёта. PATCH передаёт expected_revision и массив overrides (quantity, reason, recommendation_id). Любая правка создаёт следующую revision и снимает согласование. POST approve принимает expected_revision и confirmed=true. GET export требует revision и format=csv; нельзя скачать несогласованную или устаревшую версию. Нулевая правка допустима. Пустая/пробельная причина недопустима. Положительное количество должно соблюдать подтверждённый минимум и кратность.

Общий формат ошибок: error.code, error.message (русский), error.details. 404 — неизвестный ресурс, 409 — устаревшая версия, 422 — неверные значения или блокирующие данные, 501 — функция ещё не подключена. Сетевая ошибка никогда не включает скрытый переход к мокам.

Согласование также создаёт новую revision: черновик 1 → правка 2 → согласование 3 с approved_revision=3. Frontend всегда использует revision из последнего ответа сервера. Одновременные правки проверяются и сохраняются одной транзакцией SQLite; история версий остаётся в order_versions.
