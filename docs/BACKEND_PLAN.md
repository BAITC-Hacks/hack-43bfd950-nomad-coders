# Реальный импорт и расчёт закупки

## Назначение

Этот ExecPlan поддерживается по .agent/PLANS.md. После его выполнения капитан сможет загрузить шесть известных XLSX одного поставщика через существующий POST /api/datasets, получить объяснимый результат POST /api/calculations и сохранить заказ существующими маршрутами. Frontend принадлежит тиммейту; интерфейс API сохраняется, новые поля только с совместимыми значениями по умолчанию. Данные партнёра остаются локально.

## Контекст и интерфейсы

backend/app/ingestion.import_workbooks(list[SourceWorkbook], supplier) возвращает NormalizedDataset. Каждый набор содержит только одного поставщика, поэтому связи по строковому SKU однозначны. Расчёт engine.calculate(dataset, settings) возвращает EngineOutput и не читает файлы, БД или сеть. Service сохраняет результат и объяснения; SQLite Repository уже поддерживает атомарные версии заказов. JSON-примеры и TypeScript генерируются из Pydantic командой scripts/contracts.ps1.

## Порядок реализации

Сначала реализовать адаптеры известных заголовков, сохранить источники и пропуски. Данные читать потоково через openpyxl; маленький снимок Systeme открыть с комментариями. Не считать имя файла единственным доказательством схемы. Версия набора определяется содержимым входных файлов и поставщиком, повторная загрузка возвращает тот же набор. Битая книга или повтор одной роли выдаёт 422; проблемы отдельных SKU сохраняются в issues.

Добавить необязательное структурированное покрытие журнала: начало, конец, полнота и источник. В предоставленной выгрузке начало 2025 и конец по датам отчёта являются явным допущением известного адаптера, а не доказанной полнотой; показать предупреждение. Без покрытия нельзя достоверно заполнять пустые дни нулями. Исходные транзакции до периода не удаляются. Нет customer_id и stockout в оригиналах — проверяем эти возможности на отдельной синтетике.

Расчёт берёт один источник: транзакции или полные месяцы, без суммирования. Документы агрегируются по SKU/дате/номеру и клиенту при его наличии. Порог крупного документа строится по медиане/IQR; единичный явный всплеск исключается при достаточном фоне, повторяемые покупки сохраняются по неделям. Знаки возвратов сохраняются. Неопределённая история блокируется или получает явное предупреждение, не выдаётся за точный ноль.

Профиль 12 месяцев нормируется к среднему 1. Снять сезонность с очищенной истории, восстановить только подтверждённые дни stockout, объединяя пересечения. Скорость — по календарным дням покрытия с корректировкой отсутствия. Рост оценить по нескольким полным месяцам очищенной истории; ручной коэффициент заменяет вычисленный. Прогноз применяется к каждому будущему дню с его сезонным коэффициентом. Неполный месяц не участвует в росте как полный.

Дата расчёта — конец дня. Горизонт H = срок L + пересмотр R. Приход учитывается в начале своей даты, на/до даты снимка повторно не прибавляется. Максимум потребности по дням от max(1,L) до H предотвращает покрытие раннего дефицита поздней поставкой. Дефицит до L отмечается срочностью. Буфер в днях может переопределяться по категории. Ноль остаётся нулём; при положительной потребности сначала минимум, затем кратность. Неподтверждённые единицы и остатки блокируют строку. Ручной остаток сохраняется отдельно и с причиной.

## Проверки

Из корня выполнить .venv/Scripts/python.exe -m pytest -c backend/pytest.ini backend/tests. Для проекта Windows общий scripts/check.ps1 запускает тесты и сборку, -Browser добавляет сквозной сценарий. Данные оригиналов проверить отдельной локальной командой из Downloads, не добавляя архивы или расчёты в Git. Проверить сумму документов против строк, 10 шт/день → 144 при заданной кратности, поздний приход → 30 в примере L=2/R=3, stockout без двойного учёта, разовый всплеск против повторяемого клиента, источник monthly отдельно, missing/zero, 422 повреждённого XLSX, идемпотентность и API→CSV.

## Surprises & Discoveries

Контракт не содержал покрытия журнала; min/max одного товара недостаточно. В IEK есть смешение единиц и повторные ключи; минимум не равен кратности. Показатель роста AR в Systeme неоднозначен и не будет автоматически применяться вместо собственной оценки. Ни скрытые листы, ни встроенные внешние прайсы не являются дополнительными продажами.

## Outcomes & Retrospective

Реальный backend реализован. Локально прочитаны 724 товара/77312 транзакций Systeme и 3185/171603 IEK; импорт занимает примерно 10 и 26 секунд без записи БД, чистый расчёт — 1 и 3 секунды. IEK блокируется без текущего остатка, что соответствует ограничениям источников. API на синтетических XLSX прошёл импорт → реальный расчёт → правка в ноль → согласование → CSV. Точность на отложенном периоде не измерена. Frontend для всех настроек и облачная публикация остаются отдельными этапами.

Read-only проверка выявила и помогла исправить удаление единичного гигантского заказа среди регулярных крупных покупок, пропуск глобальной блокировки, влияние будущей транзакции, дробную кратность и конфликт stockout с исходной покупкой. Исправления покрыты регрессиями. Импорт дополнительно проверяет ошибочную дату даже при неизвестном количестве и сортирует входы для независимости от порядка загрузки.

## Повторный запуск и восстановление

Повторный импорт одинакового содержимого не создаёт новую версию и не меняет исходные наблюдения. Новые результаты расчёта получают новый id, прошлые не переписываются. Для восстановления использовать прежний коммит и сохранённую локальную базу; пользовательские файлы и ветки не удалять. Публиковать только код и синтетические тесты.
