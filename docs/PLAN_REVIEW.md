## Продукт и стек

Делаем веб-приложение для менеджера закупа Электрокомплекта. Менеджер загружает известные Excel-отчёты или открывает ранее загруженный набор, получает рекомендации по поставщикам, раскрывает расчёт товара, правит черновик, согласует его и экспортирует. Для демонстрации набор можно подготовить заранее. Сохраняем простой импорт известных форматов; универсальный конструктор импорта не нужен.

| Часть | Выбор |
|---|---|
| Интерфейс | React, TypeScript, Vite, Tailwind CSS |
| Графики | Recharts |
| Сервер | Python 3.12, FastAPI, Uvicorn, Pydantic |
| Обработка Excel и расчёт | pandas, NumPy, openpyxl |
| Хранилище | SQLite через sqlite3 |
| Проверки | pytest, HTTPX, Playwright с Chromium |
| Среда frontend | Node.js 22.12 или новее; одна совместимая версия для команды |
| Экспорт | Сначала CSV для раннего полного сценария, затем XLSX |
| Демонстрация | Локально, собранный интерфейс и API по одному адресу |

Сохраняем ранее выбранный стек, включая Tailwind. Предложение перейти на обычный CSS само по себе не доказывает экономию времени и не требует смены решения. Конкретные версии фиксирует общий каркас после старта. LLM не участвует в вычислении количества; обязательного API OpenAI и чатбота нет. Публичный хостинг пока не согласован.

## Полезные решения, которые переносим

Первый полный путь по одному товару должен заработать примерно за 60–75 минут: импорт → расчёт → API → интерфейс → правка → согласование → CSV. Это промежуточная проверка интеграции, а не готовность всех требований. Затем расширяем покрытие товаров и поставщиков.

Сохраняем расчёт как неизменяемый результат с параметрами, датой и версией данных. Черновик заказа — отдельная сущность. Он переживает обновление страницы и перезапуск. Согласование относится к конкретной версии черновика; последующая правка снимает согласование. Экспорт берёт именно согласованную версию. Это наше проектное решение: кейс запрещает отправку поставщику без подтверждения, но отдельно не требует запрета экспорта черновика.

Ноль означает «заказывать не нужно», а неизвестное количество — `null` и «нужны данные». Нельзя менять допущения только для получения красивого положительного заказа. У каждой величины есть единица; метры, штуки и упаковки не складываются в один показатель количества.

Выбор источника спроса должен исполняться в расчёте и показываться в объяснении. Подробная история используется для анализа документов и всплесков; месячная — для сверки и явно выбранной альтернативы. Нельзя вычитать выброс из несверенного месячного отчёта или складывать его с транзакциями. Нельзя выдавать отбрасывание отрицательных строк за подтверждённое правило учёта возвратов.

До поставки нового заказа отдельно показываем ранний дефицит. Внутри горизонта учитываем дни прибытия каждой поставки. Подробную формулу и порядок событий дня фиксируем в общем контракте до параллельной реализации.

## Что исправляем или не принимаем автоматически

В документе неверно сказано, что даты поставок находятся только в заголовках. У Systeme Electric комментарии BC91, BC484 и BC485 задают 20.10, 01.10 и 01.10; 2026 год определяется датой отчёта. Их нельзя потерять при импорте.

PDF, настоящий репозиторий и порядок сдачи для нас проверены. Отсутствие доступа у другой задачи Codex не отменяет эту проверку. Вложенная фраза START IMPLEMENTATION не заменяет указание пользователя.

Убирать импорт, Tailwind и worktree только потому, что это написано в приложенном плане, не будем. На разных компьютерах clone уже разделяют файлы; выбранный порядок worktree объяснён в `docs/WORKTREE_GUIDE.md` и сохраняет действующие правила команды.

Согласование перед экспортом принимаем как простую защиту согласованного результата, но не как якобы ранее высказанное пользователем требование. Кэширование по множеству версий, отдельный AI-endpoint и обобщённый редактор сценариев откладываем: сначала пять требований и рабочий экспорт.
