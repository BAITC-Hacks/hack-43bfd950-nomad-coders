# Три компьютера, один репозиторий и три задачи Codex

Команда подтвердила: каждый работает на своём компьютере. Капитан и его текущая задача отвечают за интеграцию и главную ветку. Второй участник делает данные и расчёты, третий — интерфейс. Сейчас идёт подготовка; команды ниже являются инструкцией, а не отчётом об уже выполненных действиях.

## Что означает каждое слово

Репозиторий на GitHub — общее место для сохранённых изменений команды. Clone — локальная копия этого репозитория на компьютере участника. Ветка — отдельная история изменений. Worktree — дополнительная рабочая папка Git, в которой открыта своя ветка. Задача Codex — разговор с агентом, работающим в выбранной папке.

GitHub передаёт коммиты через push и fetch/pull. Worktree сам ничего не передаёт на другие компьютеры. Три разговора Codex в одной обычной папке не изолируют файлы друг от друга. Отдельные clone на разных компьютерах уже изолированы; для нашей команды сохраняем также по одному именованному worktree на исполнителя, как указано в AGENTS.md.

| Исполнитель | Ветка | Рабочая папка рядом с clone | Область |
|---|---|---|---|
| Капитан + текущая задача | `codex/api-integration` | `nomad-api` | Контракт, API, SQLite, экспорт, интеграция |
| Участник 2 | `codex/data-engine` | `nomad-data` | Импорт, прогноз, расчёт и их тесты |
| Участник 3 | `codex/web-ui` | `nomad-web` | Интерфейс и браузерный сценарий |

`main` — общий проверенный результат. Только капитан объединяет туда изменения. «Мы главные» означает ответственность за main, а текущие изменения API всё равно удобно делать в `codex/api-integration`.

## 1. Что сначала делает капитан

Все три ветки уже существуют локально. Повторно создавать их не нужно. Пока подготовительные коммиты не отправлены, они недоступны тиммейтам через GitHub. Новые документы этой подготовки также пока не закоммичены.

После указания пользователя на передачу подготовки капитан проверяет изменения, сохраняет документацию коммитом, переносит её в три ветки обычным fast-forward/merge и публикует main и три именованные ветки. Не перезаписывать существующие удалённые изменения. Проверить доступ к репозиторию каждого участника. Это отдельный этап от написания кода.

После явного старта реализации капитан создаёт общий каркас, схемы и синтетические примеры за первые 20–25 минут. Публикует общий коммит в main и сообщает его SHA — идентификатор коммита. До этого тиммейты могут настроить Git и прочитать ТЗ, но не должны независимо придумывать контракты и каркасы приложения.

## 2. Что каждый тиммейт делает на своём компьютере

Установленный Git должен работать, а собственный GitHub-аккаунт — иметь доступ к репозиторию. Архив ZIP с кодом не заменяет clone. Команды выполняются в терминале PowerShell, по одной. Остановиться при ошибке, а не выполнять оставшиеся команды вслепую.

Перейти в папку, где будут проекты, затем один раз клонировать репозиторий:

```powershell
git clone https://github.com/BAITC-Hacks/hack-43bfd950-nomad-coders.git nomad-coders
cd nomad-coders
git fetch origin
git branch -a
git worktree list
```

Если clone уже есть, открыть именно его и начать с `git status`, затем `git fetch origin`. Повторный clone не требуется. В списке веток после публикации капитаном должны быть `remotes/origin/codex/data-engine` и `remotes/origin/codex/web-ui`. Если их нет, сообщить капитану; не создавать ветку от случайной исходной версии.

**Участник 2** выполняет из папки clone:

```powershell
git worktree add --track -b codex/data-engine ../nomad-data origin/codex/data-engine
git -C ../nomad-data status --short --branch
```

**Участник 3** выполняет на своём компьютере:

```powershell
git worktree add --track -b codex/web-ui ../nomad-web origin/codex/web-ui
git -C ../nomad-web status --short --branch
```

Это команды для свежего clone, в котором соответствующей локальной ветки ещё нет. Если ветка уже есть, убрать создание `--track -b` и ссылку на origin: например, `git worktree add ../nomad-data codex/data-engine`. Если Git сообщает, что ветка уже открыта в другой папке, найти её через `git worktree list` и использовать эту папку. Не обходить запрет через `--force`.

Для капитана, у которого ветка уже существует: `git worktree add ../nomad-api codex/api-integration`. Создание этой папки само по себе не переносит текущую задачу Codex в неё. При настройке капитан использует Handoff или продолжает работу в задаче, явно привязанной к полученному пути; до этого агент не должен писать код в прежнюю папку по ошибке.

## 3. Как открыть задачу Codex

Для понятного пути с заранее названной веткой используем worktree, созданный командами выше. Добавить в Codex как проект папку `nomad-data` или `nomad-web`. Создать в этом проекте одну задачу в режиме **Local**. Здесь Local означает работу прямо в выбранной папке, которая уже является Git worktree. Второй Worktree поверх неё не нужен.

Первое сообщение: «Прочитай AGENTS.md, planning.md, docs/TEAM.md, docs/DATA_NOTES.md и моё ТЗ. Покажи текущую папку, ветку и git status. Подтверди границы моей работы. Код пока не пиши». Для данных ТЗ — `docs/TASK_DATA.md`, для интерфейса — `docs/TASK_WEB.md`.

Проверить ответ: правильная папка, своя ветка, отсутствие неожиданных изменений. В этой папке не запускать вторую независимую пишущую задачу и не переключать ветку вручную, пока агент работает.

Альтернатива — встроенный режим Worktree в Codex. Он создаёт отдельную папку автоматически; возможна работа с detached HEAD, когда именованная ветка ещё не выбрана. Перед публикацией требуется привязать результат к нужной ветке, проверив, не занята ли она. Чтобы новичкам не смешивать два способа, выше выбран явный Git worktree и затем Local. [Документация OpenAI о worktree](https://learn.chatgpt.com/docs/environments/git-worktrees).

## 4. Получить общий каркас и начать

Капитан сообщает, что каркас опубликован, и передаёт SHA. В своей рабочей папке каждый проверяет чистоту `git status`, затем выполняет:

```powershell
git fetch origin
git merge origin/main
git log -1 --oneline
```

Не выполнять merge поверх несохранённой работы. При конфликте сохранить текущее состояние и передать капитану пути конфликтующих файлов. После получения общего коммита и разрешения начать работу отправить своему Codex стартовый запрос из ТЗ. Зависимости установить по README общего каркаса, не выбирать версии независимо.

Исходные Excel передаются участникам отдельно от Git через согласованный командой способ. Путь `C:/Users/User/Downloads` из заметок относится только к компьютеру капитана. Каждый сообщает своему агенту реальные пути. Базы, исходные данные и `.env` не публикуются. У каждого собственные runtime и окружение.

## 5. Передавать результат каждые 30–45 минут

Попросить свой Codex: «Проверь мою область и тесты, покажи diff, исключи приватные данные, сохрани только мои изменения коммитом и отправь в мою ветку. Верни SHA, результаты проверок и ограничения. main не меняй».

Коммит сохраняет изменения локально; push отправляет его на GitHub. Капитан получает ветку, проверяет diff и тесты, объединяет в main. Потом остальные получают main через fetch и merge. Незакоммиченные файлы и история разговора Codex через Git не передаются.

На разных компьютерах можно всем использовать backend 8000 и frontend 5173. Разные порты нужны лишь при одновременном запуске нескольких копий на одном компьютере. Ни worktree, ни разные ветки не устраняют конфликты при правке одного файла — для этого нужны границы ТЗ.
