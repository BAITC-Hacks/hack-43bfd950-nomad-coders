# Работа трёх участников

## Распределение

Капитан команды отвечает за API, SQLite, экспорт, общий контракт, объединение веток и сдачу. Его ветка — `codex/api-integration`. Область: общие схемы и API/storage/export-модули backend, настройки запуска и CI. Только он изменяет общие схемы, зависимости Python и главный план.

Второй участник отвечает за импорт Excel, очистку, аномалии, stockout, прогноз и количество заказа. Ветка — `codex/data-engine`. Область: import/forecast/replenishment-модули и тесты их поведения. Изменения общих схем или зависимостей предлагает интегратору.

Третий участник отвечает за React, три экрана, графики, правки менеджера и демонстрацию в браузере. Ветка — `codex/web-ui`. Область: frontend и браузерные тесты. Он владеет зависимостями frontend, а об изменениях контракта договаривается с интегратором.

Имена назначаются командой. У каждого свой основной Codex-task; задачи не должны одновременно редактировать одни файлы.

Пользователь подтвердил отдельные компьютеры и роль текущей задачи как интегратора. Подробная настройка — в `docs/WORKTREE_GUIDE.md`. Задания исполнителей — `docs/TASK_DATA.md` и `docs/TASK_WEB.md`. Результат разбора плана тиммейта и итоговый стек — `docs/PLAN_REVIEW.md`.

## Последовательность

Сначала прочитать AGENTS.md и planning.md. Подготовленные сейчас ветки содержат только документы. После явного начала реализации интегратор за первые 25 минут создаёт общий каркас и контракт. Перед параллельной разработкой остальные ветки получают этот общий commit.

Каждый получает собственный clone. Для новичков основной путь — создать именованный Git worktree по `docs/WORKTREE_GUIDE.md`, открыть именно его папку в Codex desktop и создать там задачу в режиме Local: изоляция уже обеспечена выбранной папкой. Встроенный режим Worktree — альтернативный способ, не второй обязательный шаг. Если managed worktree использует detached HEAD, для публикации результата требуется именованная ветка. Не создавать второй checkout той же ветки в одном clone. Если ветка уже существует, использовать её, а не создавать повторно.

Участникам на других компьютерах нужны свои clone и доступ к приватному GitHub-репозиторию. Локальные ветки и рабочие файлы сами не появятся на их компьютерах; GitHub синхронизирует только отправленные commits. Текущий диалог подготовки находился вне проекта; для новой задачи в проекте достаточно прочитать файлы контекста.

Не копировать общую SQLite-базу между пишущими процессами. Для worktree создавать отдельные зависимости и runtime-каталог. При одновременном запуске на одном компьютере использовать пары портов: интеграция 8000/5173, данные 8001/5174, frontend 8002/5175.

## Передача изменений

Каждые 30–45 минут передавать небольшой commit: что работает, какие проверки выполнены, какие ограничения остались. Интегратор проверяет diff, объединяет одну ветку за раз и запускает общие проверки. Остальные включают обновлённую main в свою ветку. Не использовать force push. Не откладывать первую интеграцию до последнего часа.

## Агенты

Основных пишущих задач три. Дополнительных субагентов применять к независимому чтению, проверкам и отладке. Изоляция контекста субагента не означает изоляцию файлов. Только ограниченный владелец кода исправляет замечания.

Пример запроса для проверки после реализации:

> Запусти двух read-only субагентов. Первый проверяет арифметику, аномалии, сезонность и восстановление спроса. Второй проверяет API, экспорт, правки и отсутствие публикации приватных данных. Верните конкретные воспроизводимые ошибки. Код не изменяйте.

Проверь текущую ветку и состояние Git, подтверди, что контекст понятен, и жди моего указания начать реализацию. Код приложения пока не создавай, изменения на GitHub не отправляй.
