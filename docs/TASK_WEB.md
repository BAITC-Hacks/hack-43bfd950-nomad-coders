# ТЗ frontend: рабочий интерфейс и визуальное оформление

Обновлено 23.09.2026 после публикации каркаса 1283425. Два исполнителя: капитан делает весь backend и интеграцию; тиммейт — frontend. Работать в своей папке nomad-web, ветка codex/web-ui. Это задание разрешает начинать frontend сразу после получения актуальной main.

## Перед началом

Прочитать AGENTS.md, planning.md, docs/TEAM.md, docs/DATA_NOTES.md и contracts/README.md. Проверить git status, сохранить свои изменения коммитом, выполнить git fetch origin и git merge origin/main. Команды установки и запуска — в README. Новую ветку или worktree не создавать.

Владение — весь frontend/, включая App.tsx, клиент API, компоненты, стили и браузерные тесты, кроме frontend/src/api/generated/. Не менять backend/, contracts/, planning.md, корневую конфигурацию и общие схемы. Генерируемые типы — источник форм полей, а не файл для ручного исправления. Предложения по API передавать капитану отдельно.

## Что уже работает — сохранить

Существуют три представления, клиент API, русский интерфейс, Recharts и Tailwind через Vite-плагин. Синтетика загружается командой scripts/seed.ps1; сервер запускается с -Demo. API возвращает рекомендации 144, 0 и null. Черновик сохраняется в SQLite, поддерживает правку с причиной, ноль, версии, согласование и CSV. Последний заказ восстанавливается после обновления страницы. Playwright проверяет этот путь на собранном интерфейсе через FastAPI.

Не пересоздавать проект и не заменять API статическими массивами. Реальный импорт Excel и реальный прогноз пока возвращают 501; их делает капитан. Демонстрационные числа фиксированы и не меняются от настроек. Новый интерфейс должен честно работать в этом состоянии и затем принять настоящие ответы без переделки схемы.

## Результат

Сделать спокойное, современное рабочее приложение для закупщика. Главная ценность — быстро найти товар, понять рекомендацию и проверить заказ. Сохранить три шага: данные → рекомендации → заказ. Не превращать приложение в рекламный лендинг. Пользователь должен видеть основные действия без прокрутки большого вступительного блока.

## Визуальное направление

Светлая тема: фон #F6F8FA, белые рабочие поверхности, основной текст #172B36, вторичный #526175, тонкие границы #DCE4E8. Единственный основной акцент — глубокий бирюзовый #0F766E. Янтарный использовать только для предупреждений, красный — для ошибок. Статус всегда подписан словами, а не только цветом. Без градиентов, стеклянных панелей, неона, крупных декоративных иллюстраций и множества разноцветных карточек.

Использовать общие CSS-переменные или Tailwind-токены для цветов, отступов, радиусов и типографики. Сетка отступов 4/8/12/16/24/32 px; радиус 8–12 px, тень очень лёгкая только у плавающих панелей. Основной текст 14–16 px, заголовок страницы 26–30 px, числовые колонки с tabular-nums и выравниванием вправо. Системный шрифт Segoe UI/system-ui подходит; внешние шрифты и CDN не обязательны. Если добавлять иконки, использовать один набор, без emoji вместо элементов управления.

Макет: компактная верхняя панель с названием и признаком демо; ниже название рабочего раздела и навигация трёх шагов. Максимальная ширина примерно 1440 px. На экране рекомендаций сверху строка поиска/фильтров и короткие счётчики, основную площадь занимает таблица. Объяснение открывается справа в панели шириной около 440–520 px, сохраняя контекст строки. На узком экране панель занимает всю ширину. В заказе основной акцент — таблица правок и доступное основное действие.

Каждый экран имеет одно визуально главное действие: «Рассчитать», «Создать заказ» или «Сохранить / Согласовать». Кнопки и поля одинаковой высоты, состояния hover/focus/disabled заметны. Лёгкие переходы 120–180 мс допустимы; учитывать prefers-reduced-motion. Сначала проверить 1366×768 и 1440×900, затем 768 px и телефон 390 px. Таблица может прокручиваться горизонтально внутри своей области; вся страница не должна разъезжаться.

## Этап 1. Оформление и структура, без ожидания backend

Разделить большой App.tsx на страницы DataPage, RecommendationsPage, OrderPage, панель ExplanationPanel и небольшие общие компоненты. Названия примерные; не добавлять тяжёлую архитектуру или библиотеки ради трёх экранов. Запросы проводить через src/api/client.ts, состояние заказа брать из ответа сервера. Привести существующий сквозной сценарий к новому оформлению и сразу сохранить его работоспособность.

Сжать шапку и предупреждение о демо. Сделать осмысленные пустые состояния с действием, локальную загрузку нужного блока и сообщение об ошибке рядом с действием. Ошибку сети нельзя заменять успешным моковым ответом. Переключение экрана не должно допускать поздний ответ старого запроса поверх нового выбранного товара; применять отмену запроса или проверку актуального id.

## Этап 2. Данные и настройки

Показать выбор поставщика и набора, его версию, происхождение, дату загрузки и признак синтетики. created_at — дата загрузки/создания, не дата остатков. Книги выбираются несколькими файлами; показать имена, размер, удаление из выбранного списка, допустимый XLSX и общий лимит API 30 МиБ. Drag-and-drop — удобное дополнение, но обычная кнопка выбора обязательна. Не показывать выдуманный процент загрузки: достаточно состояния «Загружаем…», если прогресс не измеряется.

Добавить форму CalculationSettings: дата as_of; lead_time_days 0–365; review_days 1–365; buffer_days 0–365; источник спроса transactions/monthly. Объяснить значения короткими подписями. Для текущего демонстрационного набора оставить фиксированные 22.09.2026, 14/7/7 и transactions, с явной пометкой «Фиксированный пример». Для реального набора передавать введённые значения серверу; 501 показывать как недоступность функции, не как успешный расчёт. Новые значения настроек должны делать прежние рекомендации визуально неактуальными до нового успешного расчёта.

Показывать dataset.issues и error.details: сообщение, уровень, SKU, источник при наличии. Не додумывать отсутствующие сведения. При успешном импорте перечитать список наборов и выбрать новый. Когда капитан подключит импорт, этот путь должен заработать без изменения frontend-контракта.

## Этап 3. Рекомендации и объяснение

Добавить поиск по названию, строковому SKU и артикулу; фильтры поставщика, категории, срочности и проблем данных. Сортировка по количеству/статусу и кнопка сброса. Счётчики: число товаров, требующих заказа, без потребности и требующих данных. Не суммировать метры со штуками и не показывать стоимость/экономию без данных о ценах. Категории показывать как коды без придуманных названий.

В таблице нужны товар, SKU/артикул, единица, категория, доступный остаток и дата его снимка, рекомендация, срочность, индикатор проблемы, открытие объяснения. Закрепить заголовок и сделать выбранную строку заметной. На тысячи товаров использовать пагинацию 50/100 строк; виртуализация только при измеренной необходимости. null сортируется и отображается отдельно от нуля, без преобразования в 0. Для 0 писать «Заказывать не нужно», для null — «Нужны данные».

Выбор блокируется при null, неизвестной единице или blocking issue. Один заказ — один поставщик. При смене фильтра не терять выбор молча: показывать число выбранных, включая скрытые строки, и кнопку очистки. «Выбрать все» явно действует на текущую страницу. Не создавать смешанный заказ разных поставщиков; объяснять ограничение перед нажатием создания.

ExplanationPanel получает GET /api/calculations/{id}/items/{item_id}. Показать recommendation.explanation; исходные величины из components, потребность raw_need до округления, minimum и multiple как разные правила, итог. Показать stock_date, источник спроса, assumptions, issues и доступные источники товара. Входящие поставки — дата, количество, единица и источник; неизвестная дата остаётся неизвестной. Не утверждать, что вся поставка входит в расчёт: её учёт объясняет backend.

График history: raw, cleaned, adjusted и forecast только если они присутствуют. Легенда по-русски, подписанные оси и единицы, форматированные даты, tooltip; пропуски не превращать в нули и не соединять искусственной линией. Прогноз отличать штрихом. Отдельно показать anomalies: документ, дата, количество, решение и причина. Growth_factor и stockout_lost_demand брать из components. Отдельных сезонных коэффициентов в ответе объяснения сейчас нет: не восстанавливать их в браузере, запросить расширение у капитана, если нужен такой блок.

## Этап 4. Заказ и надёжные состояния

Сохранить исходную рекомендацию рядом с количеством менеджера, причину, единицу и поставщика. Показать версию, дату сохранения, статус «Черновик / Согласован», состояние несохранённых изменений. Проверять неотрицательное конечное число; пустое поле не равно нулю. Причина обязательна для каждой правки. Подсказка о минимуме/кратности берётся из соответствующей рекомендации; окончательная проверка остаётся на сервере.

Сохранение передаёт expected_revision. В ответе 409 объяснить конфликт и предложить загрузить актуальную версию; введённые значения не стирать автоматически. При загрузке/выходе с несохранёнными правками — явное сохранение или отмена; закрытие вкладки защищено beforeunload. Согласование доступно только после сохранения. Само согласование увеличивает revision: использовать ответ сервера, не прибавлять вручную.

CSV скачивать через API для актуальной согласованной версии. Если экспорт получил 409 или ошибку сети, показать сообщение в приложении, не перекидывать пользователя на страницу JSON. При успешном скачивании сохранить файл из ответа сервера, не собирать CSV из таблицы. После правки согласованного заказа снова требуется согласование. Сохранять восстановление последнего заказа и загружать связанный calculation_id, чтобы после обновления страницы можно было вернуться к рекомендациям.

Список всех заказов и XLSX пока не имеют соответствующего API. Не показывать фиктивную историю и работающую кнопку XLSX. Это отдельные предложения капитану, не препятствие основному сценарию.

## Проверки и передача

Сохранить и расширить frontend/tests/workflow.spec.ts. Проверить: 144/0/null, запрет неизвестного количества, поиск и фильтры, выбор одного поставщика, объяснение, правка на 0, обязательная причина, сохранение после refresh, согласование, содержимое скачанного CSV, снятие согласования после изменения. Добавить UI-проверку 409 и 501 через явно настроенные тестовые ответы Playwright; в самом приложении скрытых моков нет.

Проверить клавиатуру и видимый фокус, label у полей, aria-label у кнопок без текста, возврат фокуса после закрытия боковой панели, Escape, доступное сообщение об ошибке. Для модальной панели — удержание фокуса внутри; для немодальной не объявлять aria-modal. Важный текст имеет контраст не ниже 4.5:1. Статус и график различимы без опоры только на цвет.

Запустить scripts/check.ps1 -Browser из корня. Playwright работает с собранным интерфейсом через FastAPI на 8009, который должен быть свободен. Снять скриншоты трёх экранов и панели на ширине 1366 px, дополнительно проверить 390 px. Большой графический код можно загрузить лениво: текущая сборка предупреждает о JS-бандле около 590 КБ; оптимизировать после сохранения сценария, не скрывать предупреждение увеличением лимита.

Первый небольшой коммит: оформление и структура + сохранённый сквозной путь. Второй: фильтры, объяснение, формы и ошибки. Каждые 30–45 минут сохранять работающий результат. Push только codex/web-ui. Передать капитану SHA, перечень функций, результаты проверок, скриншоты и список того, что ждёт backend. Капитан проверяет и объединяет main.

Если времени мало: сначала работоспособный путь и читаемая таблица, затем объяснение и фильтры, после — анимации и дополнительная полировка. Не тратить время на тёмную тему, регистрацию, роли, PDF, drag-reordering, декоративный dashboard и публичный деплой. Деплоем занимается капитан.
