# Техническое задание участнику 3 — веб-интерфейс

Статус: подготовленное задание, реализация ещё не началась. Начать после явного разрешения и получения общего каркаса от капитана. Ветка `codex/web-ui`, отдельная рабочая папка `nomad-web`. Прочитать AGENTS.md, planning.md, docs/TEAM.md и docs/DATA_NOTES.md. Настройка Git описана в docs/WORKTREE_GUIDE.md.

## Результат и границы

Сделать русский интерфейс менеджера закупа: импорт известных Excel, рекомендации по поставщикам, объяснение товара, правка, согласование и экспорт. Использовать React, TypeScript, Vite, Tailwind CSS и Recharts. Имена программных идентификаторов — английские.

Владение: `frontend/`, кроме `frontend/src/api/generated/` — типов общего контракта, которыми владеет капитан. Капитан сначала создаёт общий каркас; после его передачи конфигурацией и зависимостями frontend занимается участник 3. Не менять backend, корневые настройки, contracts/, planning.md и схемы API. Эти пути пока планируемые, реализация отсутствует.

Начать с канонических синтетических JSON-примеров из `contracts/fixtures/`, которые создаёт капитан. Примеры должны покрывать положительное количество, ноль, неизвестное количество и ошибку. Не придумывать дополнительные поля и не рассчитывать закупку в браузере. Затем подключить настоящий API без изменения модели данных. Моковый режим явно обозначить и выключить для итоговой демонстрации реальных данных.

## Порядок работы

1. Собрать три представления: «Данные и настройки», «Рекомендации», «Проверка заказа». Объяснение SKU открывать в боковой панели или раскрытии строки. При наличии сохранённого набора открывать рекомендации; пустое приложение предлагает импорт.
2. Для первого общего результата показать один товар, его объяснение и черновик, дать изменить количество, согласовать и выгрузить CSV. Подключить этот путь к API примерно к 60–75-й минуте общей разработки.
3. Добавить фильтры поставщика и категории, поиск по коду/артикулу, единицу, дату остатков, срочность и проблемы данных. Не придумывать смысл кодов категорий и сумму количества по разным единицам.
4. В объяснении показать исходный и очищенный спрос, сезонность и рост, остаток, поставки с датами, потребность до округления, правила округления и итог. Отдельно обозначить синтетику, ручные допущения и недостаток реальных данных.
5. В заказе показать исходную рекомендацию, правку и причину. Сохранять через API; после обновления страницы получать сохранённый заказ. Любая правка согласованного заказа снимает согласование. Экспортировать актуальную согласованную версию, полученную с сервера.
6. Добавить понятные состояния загрузки, пустого результата, ошибки импорта, недоступного API, отсутствующего остатка и конфликта версии. Нельзя подменять реальную ошибку API успешным синтетическим ответом.

`0` показывать как «Заказывать не нужно», `null` — «Нужны данные». Поле ручной правки допускает ноль, запрещает отрицательные и нечисловые значения; сервер повторяет валидацию. Экспорт не собирать отдельно из отображаемой таблицы: скачать файл API, соответствующий сохранённому заказу. Несогласованные изменения нельзя потерять молча.

## Приёмка

Основной путь проходит в Chromium: открыть/загрузить набор → рассчитать → отфильтровать поставщика → открыть объяснение → создать заказ → исправить количество на ноль → сохранить → обновить страницу → согласовать → экспортировать. Файл содержит сохранённые значения, включая ноль.

Дополнительная проверка: изменить согласованный заказ — интерфейс снова требует согласования; устаревшая версия получает понятное сообщение, а не затирает новый заказ. Неизвестный остаток нельзя принять за ноль. Проблемы отдельных строк импорта видны.

Проверить итоговую сборку, которую обслуживает FastAPI: открытие и обновление страницы, работа API, русский текст, графики и экспорт без внешних CDN. После подготовки окружения приложение работает локально без интернета. Это не обещание установки зависимостей без сети.

Команды сборки и Playwright берутся из общего каркаса. Не ограничиваться успешной сборкой: приложить результат браузерного сценария. Каждые 30–45 минут передавать коммит, результаты проверок, ограничения и необходимые изменения контракта.
