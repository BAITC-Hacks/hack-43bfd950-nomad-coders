# Задание капитану/backend — данные и расчёт

Текущее распределение: работу выполняет капитан/backend в codex/api-integration после общего каркаса. Отдельного участника, задачи и worktree для данных нет. Прочитать AGENTS.md, planning.md, docs/TEAM.md и docs/DATA_NOTES.md. Настройка Git описана в docs/WORKTREE_GUIDE.md.

## Результат и границы

Получить воспроизводимый расчёт рекомендуемого пополнения с объяснениями и проблемами данных. Владение: `backend/app/ingestion/`, `backend/app/engine/`, `backend/tests/ingestion/`, `backend/tests/engine/`, `backend/tests/fixtures/`. Последняя папка содержит только явно синтетические данные.

Капитан владеет всем backend, общими схемами и planning.md и обновляет их совместимо при необходимости. Общий каркас и контракт уже существуют. Не менять frontend тиммейта, кроме генерации общих типов. Не заводить несовместимую копию модели.

Импорт читает файлы и возвращает нормализованные записи и отчёт проблем. Расчёт принимает записи и настройки, возвращает результат; не открывает файлы, не обращается к БД, HTTP и LLM. Сохранение результата делает капитан.

## Порядок работы

1. Проверить наличие оригиналов по своим локальным путям. Открыть исходники, не полагаться только на пересказ. Отсутствующие файлы назвать.
2. Сначала импортировать Systeme Electric и рассчитать один реальный товар, например `030200193_`. Проверить значения по исходникам, включая комментарий о поставке 01.10.2026. Передать капитану результат по общей схеме для ранней интеграции.
3. Расширить импорт на шесть книг Systeme и затем шесть IEK. Сохранять артикул, код 1С, единицу, источник, лист/ячейку либо строку, дату и признаки отсутствующих значений. Выявлять повторные ключи до объединения таблиц.
4. Реализовать выбор источника спроса, очистку разовых всплесков, сезонность и устойчивый рост. Сохранять исходные наблюдения и причины решения. Анализировать объём документа, а не отдельной строки; повторяющиеся крупные покупки не удалять автоматически.
5. Реализовать восстановление спроса по явно заданным stockout-интервалам и проверку покупок анонимного клиента. Для отсутствующих реальных полей использовать отдельные синтетические наборы, не дописывать фиктивные значения в реальные данные.
6. Вычислить потребность с датированными поставками, доступным остатком, страховым запасом, минимальной отгрузкой и подтверждённой кратностью. При нехватке обязательных данных возвращать `null` с причиной; корректный нулевой заказ возвращать как `0`.

Срок поставки, дата расчёта, горизонт пересмотра и буфер передаются настройками, а не спрятаны в коде. Не считать сентябрь полным месяцем, не применять рост и сезонность дважды, не прибавлять восстановленный исторический спрос второй раз как долг. Одинаковые продажи из месячных отчётов и транзакций не суммировать. Отрицательные количества не превращать в положительные.

У Systeme использовать свободный остаток AZ, не вычитать резерв повторно. Комментарии BC91/484/485 обязательны. У IEK месячный остаток не является актуальным снимком; без подтверждённого остатка или явного ручного ввода текущий заказ блокируется. Минимум отгрузки IEK не означает кратность, а текст в названии не подтверждает преобразование упаковки в метры.

## Приёмка

Из одной зафиксированной версии входов и настроек получается одинаковый результат. Каждый заказ объясняется числами, источником спроса, датами и правилами округления. Исходные данные не изменяются.

На синтетике: спрос 10 шт/день, срок 14 дней, пересмотр 7 дней, буфер 7 дней, остаток 100, поставка 40 к началу горизонта → потребность 140; кратность 12 → заказ 144. Более ранняя подходящая поставка не повышает заказ; поставка после горизонта его не уменьшает. Поздняя поставка не скрывает ранний дефицит.

Единичный большой выброс не должен существенно увеличивать регулярный прогноз, включая расчёт роста; устойчивый рост и повторяемые покупки сохраняются. Сезонный профиль меняет прогноз. Подтверждённый stockout повышает оценку относительно сырых продаж без двойного счёта. Отдельно проверить пропуск против нуля, смешанные единицы, нехватку истории, дубли ключей и три комментария поставок.

Команды pytest берутся из общего каркаса после его появления; в отчёте указать фактически выполненные команды и результат. Каждые 30–45 минут передавать коммит, список проверок, ограничения и необходимые изменения контракта.

## Стартовый запрос в свою задачу после разрешения

Исторический запрос отдельному исполнителю больше не применяется: данные и интеграцию выполняет капитан. Реализация завершена в ingestion/excel.py и engine/{demand,planning}.py, проверена на обоих локальных архивах и синтетических тестах. Выполнено 49 pytest и браузерный сценарий. Полнота журнала — допущение, точных stockout и customer_id в оригиналах нет, текущие остатки IEK требуют уточнения. Подробности выполненного этапа: docs/BACKEND_PLAN.md.
